# Design Review — 2026-10-05

## Prefer Named Section Roots With Inheritable Base Directories

Status: proposal

Use a labeled `sections` block as the stable, client-facing content root and
use an inheritable `basedir` attribute to describe the library's physical file
layout:

```hcl
sections "agents" {
  basedir = "content"

  section "workflow" {
    basedir = "workflow"

    section "foo" {
      title  = "Foo"
      source = "foo.md"
    }
  }
}
```

With relative base directories composed through the section hierarchy,
`foo.md` resolves to `<library-root>/content/workflow/foo.md`. A client can
continue to select `from = "company:agents"`, where `agents` is the logical
section-root name rather than a physical directory name.

This design keeps file-location context near the sections it affects, permits
subtrees to organize their own files, and decouples the public client contract
from the server repository layout. Before adoption, specify path composition,
root-containment validation, override behavior, and migration from
`content.markdown_root`.

## Put Choose Defaults on Their Child Sections

Status: proposal

Keep `curate = "choose"` on the parent section, but declare each choice's
default directly on the corresponding child:

```hcl
section "workflow" {
  title = "Workflow"
  curate = "choose"

  section "foo" {
    title   = "Foo"
    default = false
  }

  section "bar" {
    title   = "Bar"
    default = true
  }
}
```

This design replaces the parent's string-keyed `defaults` map. It keeps each
default beside the section it governs, removes duplicated child names, and
makes section renames less error-prone. Validation should continue to require
every direct child of a `choose` section to declare a default, while rejecting
child defaults where the parent offer does not use them.

## Consider Block-Based Client Selection

Status: possibility

Consider representing client selections as nested blocks rather than an object
whose user-defined section names share a key namespace with Mogent controls:

```hcl
source "company" {
  from = "company:agents"

  select {
    else = "exclude"

    section "policies" {}

    section "workflow" {
      accept_defaults = true
    }
  }
}
```

In this shape, section names appear as `section` block labels, while reserved
selection controls remain attributes. HCL still permits an unquoted identifier
as a block label, but its role remains visually distinct. The block hierarchy
could also mirror nested library sections and avoid reserving ordinary section
names merely because they match a selection control.

## Compose Tree Outputs as Ordered Opaque Overlays

Status: recommendation

Allow multiple source trees to contribute to one output tree. Treat every file
as opaque and apply source blocks in declaration order, with later sources
taking precedence:

```hcl
output "agent-tree" {
  path = ".agents/"
  kind = "tree"

  source "company" {
    from = "company:agent-files"
    into = "."
  }

  source "company" {
    from = "company:skills"
    into = "skills"
  }

  source "personal" {
    from = "personal:skills"
    into = "skills"
  }

  source "repo" {
    from = "repo:agent-overrides"
    into = "."
  }
}
```

Directory entries merge recursively. At the same destination path, a later
file replaces an earlier file, and a later file/directory type replaces the
earlier object. `plan` should report shadowed paths and their layers for
visibility, but shadowing is not an error and does not require a separate
resolution declaration. Mogent should preserve file modes, retain its existing
symlink and non-regular-file safety checks, build the final tree in a staging
directory, and install it transactionally.

The tree compositor understands only layer order, mount paths, relative file
paths, bytes, modes, and whiteouts. It does not distinguish skills, Markdown,
configuration, scripts, or other `.agents` content. A typed output such as a
Markdown render remains a separate, explicitly selected operation rather than
implicit behavior inside a tree overlay.

### Keep `.mogent/state.json` Authoritative

`.mogent/state.json` is the authoritative record of which output files and
directories Mogent manages and the hashes describing their contents. Planning
and applying must use that record to detect additions, removals, and direct
edits and to decide whether replacing the output is safe. The state record must
cover the complete materialized result, not just the highest-precedence layer.

Git may display a useful review diff for repositories that commit generated
outputs, but Mogent must not rely on `git diff`, repository state, or any other
external mechanism for management or hash tracking. This keeps behavior
consistent for ignored files, untracked files, and workspaces that are not Git
repositories.

### Require Generic Whiteouts

An upper layer must be able to hide a file or directory supplied by a lower
layer. Whiteouts are generic path operations and do not require Mogent to know
the purpose or format of the affected content. An illustrative client-side
shape is:

```hcl
source "personal" {
  from = "personal:skills"
  into = "skills"

  whiteout = [
    "obsolete-skill",
    "review",
  ]
}
```

Each whiteout is relative to the source's `into` mount. The layer removes the
named lower path before copying its own content, so it can either suppress the
path completely or replace an entire lower directory without retaining stale
children. `plan` must show whiteout removals and their originating layer.
Whiteout paths must remain relative, contained within the output, and unable to
traverse symlinks. Their on-disk representation, and whether declarations live
in the client configuration or library metadata, remain open design details;
they must be portable rather than depend on operating-system-specific device
nodes or extended attributes.
